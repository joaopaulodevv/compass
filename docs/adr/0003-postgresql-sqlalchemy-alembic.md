# ADR-0003: PostgreSQL with SQLAlchemy 2.x and Alembic

- **Status:** Accepted
- **Date:** 2026-10-09

## Context

Compass stores financial history: accounts, transactions, goals, profiles,
recommendations. The data is relational (a transaction belongs to an account, which
belongs to a user), monetary amounts must not be stored as floats, and the analytical
queries that matter - cash flow per month, spend per category, recurring payment
detection - are aggregations over a user's transactions in a date range.

The schema will change repeatedly as the domain is built out, so schema evolution has to
be a routine, reviewable operation.

## Decision

- **PostgreSQL** as the primary store. Transactions, strong constraints, `NUMERIC` for
  money, timezone-aware timestamps, window functions for recurrence and cash-flow
  analysis, and `pgvector` available should the vector-store question be revisited.
- **SQLAlchemy 2.x** with the typed declarative mapping (`Mapped[...]`,
  `mapped_column(...)`) and the asyncio extension over `asyncpg`.
- **Alembic** for migrations, with the async environment template. `migrations/env.py`
  reads the URL from application settings and the metadata from `Base`, so migrations and
  the application cannot target different databases and no connection string is
  committed.
- An explicit constraint/index **naming convention** on `Base.metadata`, so autogenerated
  migrations produce stable, reviewable names instead of backend defaults.
- Engine and session factory are created **lazily** and cached, so importing the
  application does not require a reachable database.

Phase 1 ships exactly one table, `users`. It validates connectivity, the ORM mapping, the
migration path and the readiness probe. Further entities arrive with the code that
computes on them.

## Consequences

- Typed models are checked by mypy in strict mode; a mistyped column is a type error
  rather than a runtime surprise.
- Autogenerated migrations are reviewable and reversible; both `upgrade()` and
  `downgrade()` of the initial revision are exercised.
- Every future financial table carries `user_id`, so per-user isolation is a schema
  property that authentication later plugs into.
- Cost: async SQLAlchemy has sharper edges than the sync API - lazy loading of
  relationships must be explicit, and session lifecycle mistakes surface as greenlet
  errors.
- Cost: autogenerate is a drafting tool. Generated revisions must be read before they are
  committed; this is written down in `docs/development.md`.

## Alternatives considered

- **No ORM (raw SQL + asyncpg).** Fastest and most explicit, but every aggregation,
  mapping and migration becomes hand-written, and the typed model layer is genuinely
  useful as the domain grows.
- **SQLModel.** Less boilerplate by unifying Pydantic and SQLAlchemy models, but it
  couples the API schema to the database schema - exactly the coupling to avoid when the
  wire format and the storage format evolve for different reasons.
- **Tortoise ORM / Piccolo.** Async-native and pleasant, with much smaller ecosystems and
  weaker migration tooling than Alembic.
- **MongoDB.** Flexible ingestion of provider payloads, but the relational integrity and
  aggregate queries that this domain is made of would have to be rebuilt by hand.
